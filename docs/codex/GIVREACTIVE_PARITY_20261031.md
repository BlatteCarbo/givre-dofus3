Status vocabulary:

- **Implemented**: concrete source path from setting/event through action exists; not proof a server accepted it.
- **Partial parity**: mechanism exists, but independent controls or semantics differ.
- **Prerequisite only**: a real supporting component exists, but not the requested complete feature.
- **Static defect/risk**: source supports the stated failure mechanism; no claim of live reproduction.

## Executive findings

Do not re-port achievement claiming or fight locks wholesale: current already has both, including settings and action consumers. The useful small port is an independent placement selector. The largest actual missing capability is an already-connected Socket session acquiring a visible game client without a new login. The old code has a guarded replay/mirror implementation; current has only a character-selection parking primitive.

An "approach toggle" needs a precise label: current already has per-spell `AllowApproach`, but it does not prohibit aggressive end-of-turn approach. Old source examined has a distance threshold and separate tactics, not a verified global Boolean approach switch. Current compatibility `setApproachDistance` does not preserve the old exact-distance posture semantics.

The screenshot's checked spectator/team locks is not evidence of successful server state. Both trees contain actual lock code, but a send and a checked box are distinct from an observed server confirmation.

## Important limitations in the old mirror code

The old implementation must not be described as universally functional:

1. `OLD/EasyBot/Sockets/SwitchSocket.vb:90-94` explicitly requires `ScopedProtocol3744`. Its presence does not certify a different active game version. `TryArmCurrentWorldMirror` can legitimately reject a loaded Socket session.
2. `SwitchSocket.vb:125-144` requires nonempty CharacterList, CharacterSelection, CharacterLoadingComplete, MapCurrent and MapComplementary snapshots from the same session. HUD presence is logged at `:117-122`, but the required-array check does not itself prove every HUD subsystem initialized.
3. `SwitchSocket.vb:48` sets `WorldMirrorPausesScript = False`. Later comments claiming manual-control pause retention (`:238-241`) are not evidence the Lua farm is paused: the actual cooperative-pause branch is conditional at `:160-179`. Decide viewer-only versus manual-control ownership before copying it.
4. Old default Socket click now means **minimize** for an attached client (`BotformSwift.vb:5557-5567`), not necessarily a real transport conversion. The actual destructive close route is different. Preserve this distinction in the new interface.

## Concrete current defects or semantic traps worth separating from ports

### 1. Approach-distance compatibility is not equivalent

Old Distance posture returns toward the preferred distance even when too far (`OLD/.../PacketsFight.vb:924-946`). Current `fightBasic:setApproachDistance` changes only a minimum (`CUR/.../GivreLuaHost.SnowMap.cs:432-437`). With no upper band, a Fleeing profile already in spell range and beyond that minimum can remain beyond the requested distance; if too close, it can retreat farther than the requested distance (`LaunchService.Combat.Turn.cs:1453-1471`). This is an implemented API with different semantics, not a no-op stub.

Minimal correction depends on intended compatibility: represent a preferred distance independently, or use an explicit equal min/max band only for that compatibility override after accounting for zero/disabled semantics. Do not change all existing kite profiles as a side effect.

### 2. Disabling per-spell approach does not mean immobile combat

Current per-spell check at `LaunchService.Combat.Turn.cs:1092-1095` is real, but the style movement at `:1380-1419` does not consult it. This is only a bug if the UI promises a global freeze; under the documented per-spell contract it is expected behavior. Explain it in the interface and offer an explicit global control if requested.

### 3. Explicit achievement claim accepts an unrelated receipt

`CUR/GivreClone.App/Services/LaunchService.LotM.cs:214-220` waits for any `AchievementRewardResultEvent`, reads its ID, updates that ID, then returns its success without requiring `rid == requested id`. Auto-claim uses a separate nonblocking send (`:232-239`), so overlapping auto/manual activity provides a plausible unrelated receipt source. **Static correlation defect; not live-reproduced.** Add an exact requested-ID predicate to the existing send-and-wait call and test unrelated-success-before-matching-rejection. Do not replace the ledger or disable automatic claims.

### 4. Old implemented code is not automatically good code

The old regeneration assignment and mirror pause/comment mismatch above are direct counterexamples. Old achievement queue reports actual receipt separately but does not guarantee retries after a missing receipt (`MITM.vb:9449-9468`). Treat its controls and policies as candidates, not a working reference for every transport behavior.

## Minimal port order, estimated cost and risks

Estimates are engineering judgment for implementation plus offline tests, not measured facts; live game validation is additional.

1. **Independent placement UI/policy: 0.5-1.5 days, low-to-medium risk.** Existing scorer/forge is reusable. Preserve style default for existing profiles, clone/import and script ownership.
2. **Clarify approach + optional global movement control: 1-2 days, medium risk.** Existing per-spell toggle is already useful. Audit aggressive end movement, Fleeing band, challenge-imposed movement and simulator together. Decide exact-distance compatibility explicitly.
3. **Repair achievement receipt correlation and expose lock/claim confirmation status: 0.5-1 day, low-to-medium risk.** No wholesale old-code copy needed. Keep server-confirmed versus injected state distinct.
4. **Optional same-side stranger kicking: 0.5-1 day, medium risk.** Existing sender remains. Avoid treating names, lock preferences, or enemy player presence as sufficient eligibility.
5. **Ordered stat caps and regeneration settings: 1-3 days each, medium risk.** Reuse current identity/session-safe upgrades and authoritative life updates. Team readiness needs policy for offline/missing members; do not fabricate full HP.
6. **Socket/visible-game continuity: several days to over a week, high risk.** This is a transport/session feature, not a button patch. Build fresh-session parked ownership first, verify bootstrap replay with exact protocol fields, then consider already-in-world cache snapshots, stale-generation rejection, manual/view-only ownership, cancel/close and upstream continuity. Old protocol guard and pause mismatch forbid assuming a copy is already functional.
