# SneakyBass/dfs source study - November 2, 2026

## Decision

`SneakyBass/dfs` is not a combat simulation/search library. At the inspected
revision it is a C++ Dofus 3.0 proxy with an event-driven resource-farming bot,
map conversion and pathfinding. Its explicit combat transition disables the
bot. Do not use its name (`dfs`) as evidence of depth-first combat search, and
do not claim Sram, Roublard or companion AI support from its protocol files.

Useful transfer is limited to historical protocol shape, map coordinates,
asset-export pointers and pathfinding comparison fixtures. The sibling combat
planner already implements substantially more predictive combat behavior.

## Exact implemented state transitions

1. State follows requests/events, then the bot chooses an action. This is the
   documented architecture, not a speculative branch simulator
   ([DOCS.md:48-52](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/DOCS.md#L48-L52)).
2. The runnable policy waits for an update, requires active/map/not-moving/
   not-collecting/not-changing-map, chooses nettle or ash resources, moves or
   interacts, then follows a map tour
   ([simple-farming-bot.cc:27-160](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/bot/src/simple-farming-bot.cc#L27-L160)).
3. On an event whose type URL ends in `jaz`, `ParseEvent` sets `Active=false`,
   sets `InCombat=true` and returns. The string identifies what the source
   treats as combat; it is not independently verified as today's message
   binding. `ClearState` resets `InCombat=false`
   ([messages.cc:851-865](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/bot/src/messages.cc#L851-L865),
   [bot.cc:159-169](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/bot/src/bot.cc#L159-L169)).
4. `BotState` contains generic positions/movement, player collection state,
   monster-group count/level, map and collectibles. There is no predictive
   fighter AP/MP/HP/shield/state/mark/bomb/cooldown model
   ([bot-state.hh:16-40,80-96](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/include/bot-state.hh#L16-L96)).
5. Movement marks the player moving, sets an effectively distant arrival time,
   sends a movement request, and later confirms based on received/timed state.
   Stationary other actors populate occupied cells
   ([bot.cc:27-90](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/bot/src/bot.cc#L27-L90),
   [bot.cc:127-154](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/bot/src/bot.cc#L127-L154)).

There is no implemented cast/effect transition, damage/heal/resistance formula,
effect-duration tick, trigger resolver, action rollback or opponent reply
simulation in this first-party runtime. The exposed request/event handler
enums and forge methods are map/chat/interactive oriented, not fight casting
([messages.hh:32-84](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/include/messages.hh#L32-L84)).
Even character-characteristics events only print a receipt
([messages.cc:903-911](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/bot/src/messages.cc#L903-L911)).

## Movement, LoS and search budget

- Board constants are 14 by 20 doubled rows (560 cells), with coordinate
  helpers. `Los` and `NonWalkableDuringFight` exist as map fields
  ([map.hh:10-24,48-84](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/include/map.hh#L10-L84)).
  They are loaded from JSON
  ([game.cc:137-156](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/bot/src/game.cc#L137-L156)).
- `MoveTo` passes `!InCombat` as the diagonal flag, but leaves
  `allow_through_entity=true` at its default. That is not fighter collision,
  tackle or AP/MP legality
  ([bot.cc:62-87](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/bot/src/bot.cc#L62-L87),
  [map.hh:36-37](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/include/map.hh#L36-L37)).
- `PointMov` uses `Mov`, elevation and move zones. The fight-specific
  `NonWalkableDuringFight` condition and fight obstacle rules are commented
  TODOs; `end` and `avoid_obstacles` are explicitly unused
  ([pathfinding.cc:217-264](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/bot/src/pathfinding.cc#L217-L264)).
- Pathfinding uses a priority queue of F-cost nodes, a closed set, cardinal
  cost 10, diagonal cost 15, heuristic scale 10 and elevation tolerance 11.
  Occupied cells can cost 20 rather than forbid passage. Speed and alignment
  biases also affect G-cost. This is A*-style weighted navigation, not a
  guaranteed shortest combat-MP route
  ([pathfinding.cc:27-30](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/bot/src/pathfinding.cc#L27-L30),
  [pathfinding.cc:127-168](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/bot/src/pathfinding.cc#L127-L168),
  [pathfinding.cc:171-215](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/bot/src/pathfinding.cc#L171-L215),
  [pathfinding.cc:267-397](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/bot/src/pathfinding.cc#L267-L397)).
- Search runs until the open queue empties, not until a combat work/depth/time
  budget is exhausted. It does not stop when the target is first reached.
  Missing target parents fall back to an auxiliary closest cell; smoothing
  and direction compression follow
  ([pathfinding.cc:296-504](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/bot/src/pathfinding.cc#L296-L504)).
- No spell line-of-sight ray/segment test is implemented in the audited
  runtime. Loading `Los` is not LoS enforcement. `SpecialEffects` bit 2 only
  changes path weight; it is not spell-effect simulation. In fact the JSON
  loader shown above does not populate `SpecialEffects`.
- Pathfinding tests contain nine named route cases, not combat legality,
  LoS, traps, bombs or bounded tactical-search tests
  ([pathfinding tests:21-173](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/bot/tests/src/pathfinding.cc#L21-L173)).
  Their existence is source evidence only; they were not run in this study.

## Spells, masks, grades, constraints and historical effect IDs

There is no upstream target-mask parser, zone/effect targeting engine,
per-grade spell database reader, state-criterion evaluator, cast-cap tracker
or cooldown legality implementation. `GameData::Initialize` parses coordinates
and the world graph, not spells
([game.cc:312-323](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/bot/src/game.cc#L312-L323)).

The schemas do carry spell IDs and levels: `SpellsEvent` has human/mutant
spell lists and `SpellItem` has `spell_id`/`spell_level`
([spell.proto:67-76](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/proto/game/spell.proto#L67-L76)).
`GameActionFightEvent.TargetedAbility.SpellCast` also carries those fields
([game_action.proto:226-242](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/proto/game/game_action.proto#L226-L242)).
These are serialized facts, not proof of grade selection or legal casting.

Critically, `action_id`, removable-effect `effect_id`, effect-instance `uid`
and `spell_id` are distinct fields
([common.proto:1080-1097](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/proto/game/common.proto#L1080-L1097)).
DFS supplies no action-ID-to-semantic table that validates the sibling's
`Classify`/`IsCertain` numeric mappings. Familiar historical IDs do not prove
current semantics, parameters, element encoding, duration, target mask,
trigger ordering or grade compatibility. The runtime also hard-codes dated
obfuscated type URLs
([messages.cc:40-78](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/bot/src/messages.cc#L40-L78)).
Do not import those URLs into the current decoder without current captures.
The pathfinder comments cite older ActionScript `DofusInvoker` map/pathfinding
sources ([pathfinding.cc:18-23](https://github.com/SneakyBass/dfs/blob/25841695b655492ca313a2ba7d694c0c05a8c4e2/bot/src/pathfinding.cc#L18-L23)).
That is historical navigation provenance, not a claim that all Dofus 2
combat effect IDs or rules transfer to Dofus 3.

## Comparison with current local combat work

Local references below are **mutable workspace observations**, not immutable
upstream citations. Root: sibling `combat-planner-slice1`; primary comparison
note: `docs/codex/RECOVERY_COMBAT_20261102.md` in the main worktree. That note
reports the sibling baseline as `e66edcc` plus uncommitted recovery work; this
study does not turn that working state into a release or integration claim.

- `GivreClone.App/Services/Combat/SpellDescriptor.cs:20-92` retains raw
  per-effect data and admits only recognized masks (`C/c`, `a`, `g`, `A`),
  immediate certain point damage 96-100, heals 108/143/407, positive-duration
  shield 1040, and sole-effect free-cell teleport 4. Unknown tokens fail
  closed. Spell targets are the intersection across effects; nonempty state
  criteria or uncertain effects prevent planning. Classification of pull,
  push, swap, buff and summon does not enable their transitions.
- `GameNameResolver.cs:462-468,558-707` reads per-grade installed bundle facts:
  AP/range/flags/caps/cooldowns/state criterion and effect action/mask/zone/
  duration/trigger facts. Immediate trigger `I` is accepted; other triggers,
  delays/random conditions remain conditional. Grade lookup prefers exact,
  then highest at or below requested, then highest available. This fallback
  is observable local behavior, not proof that a substituted grade is legal.
- `CombatTurnPlanner.cs:10-60` has immutable snapshots and explicit nodes for
  AP/MP, life/shield, cast histories and position; beam width 8, cast depth 3,
  shared work cap 180,000. Unlike DFS it performs predictive combat actions.
- `CombatTurnPlanner.cs:82-119,143-245,317-342` builds conservative enemy
  reach/fire threat maps with half-budget limits, explores paths with observed
  tackle loss (unknown losses forbid departure), checks range/alignment/LoS/
  occupancy, updates immediate life/shield/AP and teleport position, and
  considers walking between casts and at the end. Truncation is signaled.
  This is bounded approximate beam search, not exhaustive optimal play.
- The planner has no bomb, trap, visibility, duration-expiration or active-state
  field in its predictive node. DFS supplies none of those missing transition
  implementations. It must not be used to justify relaxing `CanPlan`.
- The recovery note records separate controlled-actor budgets, cancellation
  and cooldown-history fixes, then explicitly says class transitions remain
  unsupported. It also records installed grade/state/mask evidence for
  Attirance, Transposition and Entourloupe. Those current installed facts take
  precedence over generic interpretations of old names or numeric IDs.
- Recovery records 53 targeted passes after the budget correction and a full
  suite with 3,935 passes, one existing Lua raw-line-ending inventory failure
  and two ignored tests, followed by a 42-test characteristics-preservation
  run and successful app build. These are reported prior results, not checks
  executed by this study and not a live combat validation.

## Actionable follow-ups and missing evidence

1. Keep the restricted planner admission gate. Use current per-learned-grade
   bundles and deterministic fixtures for each newly supported action,
   including masks, states, duration and trigger semantics. DFS cannot verify
   the current effect-ID table or replace that data collection.
2. Use DFS schemas only as a checklist when resolving current visibility,
   mark add/remove/activate/trigger, actor show/refresh and control messages.
   Missing evidence: present-client bindings/field identities and offline
   captures proving updates, removals, resume and ordering. Do not copy `jaz`
   or other old obfuscated URL strings.
3. Before Sram transitions, preserve authoritative mark ownership/geometry,
   active status and visibility facts in live snapshots, then specify hidden
   position uncertainty and trigger order. Add offline trap placement,
   crossing/activation/removal and reveal regressions only after semantics
   are established. Generic `TRAP` enum coverage is insufficient.
4. Before Roublard setup search, obtain current bomb template/owner/element,
   state/age/combo and wall/detonation dependencies, plus the actual learned
   grades and conditional masks for movement/setup spells. Extend predictive
   state and shared planning/dispatch legality before valuing zero-damage
   placement, swaps, walls or chain effects. DFS has no implementation to port.
5. For controlled actors, compare current switch/revoke/resume payloads with
   the schema checklist, preserving actor-specific stats/spells/cooldowns and
   cancellation epochs. Missing evidence: actual current resume/reconnect
   behavior, not just declared slave fields. Retain existing local isolation
   of owner versus controlled actor facts.
6. If navigation parity is investigated separately, adapt fixed DFS route
   cases as comparison inputs, not combat truth. Include occupied blockers,
   fight-only nonwalkability, LoS walls and tackle in local tests. Do not port
   speed-weighted movement or its obstacle TODOs into MP reachability.
7. Preserve deterministic work accounting and conservative threat truncation
   in the sibling. DFS contributes no tactical budget policy. Future multi-
   action class setup needs state-aware branching and bounded tests, not
   merely a larger depth/beam or a list of class presets.

No current-client wire compatibility, exact patch support, complete effect-ID
semantics, class-specific simulation or successful companion operation can be
established from this source. These are missing evidence, not hidden completed
features. This deliverable is a source study only; project code/settings,
shared recovery text, upstream binaries and the live client were untouched.
