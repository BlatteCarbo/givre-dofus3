# Four additional Dofus repositories: native Givre automation

Research date: **2026-10-31**, source observations approximately **19:20-19:29 UTC**. Owner: child task `st_01a19356`. This supplements, and does not modify, `findings.md`. No installations, executable downloads, game actions, authenticated service calls, uploads, account writes, or shared-code edits occurred. Only this report was created in the owned temporary directory.

## Recommendation

Prioritize **native workflows that consume Givre's existing state and execute through its existing action controller**, not buttons that merely open another site:

1. **FM preset + Start/Stop**, using STAKK as an implementation reference. It has an actual decision/execution/observation loop, unlike a calculator. Its GPL-3.0-only license is a material code-reuse constraint.
2. **Metamob settings + Synchronize**, for soul/archmonster collection reconciliation. The service exposes a suitable account API and the SDK is MIT; use native C# HTTP rather than ship Node just for the SDK.
3. **Craft target + quantity/budget + Run**, combining Dofus-Craft's recursive purchase/craft planning model with a native inventory/bank/workshop execution state machine. Dofus-Craft alone does not execute crafting; BillBot demonstrates the execution side. Neither has a project source license in the inspected tree.
4. **Optional HDV price contribution toggle**, using Dofus-Craft's dedicated per-user-key batch API only after the operator provisions access. This is genuine automated upload, not a public anonymous bulk-ingest entitlement.

These are integration proposals, not claims that Givre already exposes every required command. This child did not inspect Givre's private/shared source contracts.

## Account writes, upload restrictions and correctness traps

### Metamob: account synchronization is possible, but not a blind counter upload

First-party docs require a personal API key in `Authorization: Bearer ...`, available from the user's Metamob settings. The key grants account access; own-quest endpoints reject other users' slugs. Limits are **60 requests/minute/key**, `Retry-After` on 429, and at most **200 monsters/batch**. Use absolute owned quantities, not increments: sending the same snapshot twice should not duplicate holdings. Do not change trade overrides or quest settings as a hidden side effect of synchronization. Marking a conversation read is also a remote account write. [M1, M2]

**Verified mismatch:** current first-party API docs state quantities **0-30**, while SDK `quests.ts` comments say **0-99** and the actual shared `count()` validator only checks nonnegative integer, with **no upper bound**. Do not rely on SDK validation to establish service limits. Enforce the first-party documented bound for an integration and expose an out-of-range condition without silently clamping/losing counts; actual authenticated server behavior above 30 was not tested. [M1, M3]

For one-button reconciliation, settings must choose which local holdings belong to this remote quest. Aggregate soul contents by stable monster IDs/game version, deduplicate observed item UIDs, include only complete selected storage scopes, compare with remote quantities, send the changed records in batches, and report acknowledged changes. Multiple quests/characters/storage scopes make replacing all remote values from one bag incorrect. This algorithm is a recommendation based on API semantics, not functionality supplied by the SDK. [M2, M3]

### STAKK: local does not mean no external account mutations

README says no STAKK subscription/cloud account; accounts are stored locally with Ankama API key, refresh token and Shield certificate. `key-refresh.js` actually calls Ankama refresh endpoints, can rotate tokens and persists the replacements; launch/authentication also contacts Ankama. Thus do not wrap STAKK's whole launcher just to get FM: it would introduce a second account/session authority and native hooks/proxy. The source is not evidence of a zero-egress tool or an API licensed by Ankama. [S1, S2, S5]

FM `Start` defaults to simulation if no recognized `transport` is provided. A button wired to the HTTP endpoint without explicit live transport can show successful simulated forging while doing no game work. Conversely, merely seeing a current built-in profile does not prove current-client success. Bind native Start to verified live Givre state, make simulation a separate mode, await authoritative rune/item events and expose stop reason and run results. [S2, S3]

The "all copies" queue runs one item to completion and then polls until item stats change; it asks for the next item in the workshop. A fully automated Givre queue needs its own item-selection action between copies, not a UI label that promises a finished queue. [S2]

### Dofus-Craft: use the correct API identity, not a scraped frontend key

- **Personal prices:** native local planner can keep all prices private. Existing website defaults to **community mode**, where contributions carry item/server/price and per-device ID. "Personal mode sends nothing" is too broad: `recordVisit()` posts an anonymous device presence on production app load **regardless of price mode**. Rebuilding a native planner need not inherit this analytics path. [D1, D4]
- **Automated price contribution:** dedicated routes are `GET /sniffer/config` and `POST /community-price/batch`, with an **operator-provisioned active per-friend sniffer key**, not the shared frontend `COMMUNITY_API_KEY`. Source enforces build/mapping ID, minimum tool version, known server, max **200 observations/batch**, and a **5,000 accepted-contribution/day/key** admission limit. Authenticated config reads update key last-seen state, so they are not entirely side-effect-free on the remote DB. No such request was made. [D5]
- A valid sniffer request states the **actual decoder mapping used**. Givre's own already-decoded events may not have the provider's mapping provenance. **Do not invent a mappingId or pretend Givre is SniffSniffSquared.** Ask the operator for an approved native-ingest contract/key (or an agreed mapping association) before enabling uploads. A public read API can supply reference prices without granting write access. [D5]
- **FM group data:** Discord OAuth verifies membership in the configured guild; site session token authorizes user actions; `FM_BOT_API_KEY` separately authorizes bot events/command queue. Those credentials are not interchangeable. Starting a hosted session may eventually create/change Discord content via its bot; a local Givre FM journal should not send messages or create channels unless the user explicitly opts into that integration. [D2, D3]
- **External price refresh:** Huzounet access is recorded as permission obtained by this project's author, with `READ_SERVERS = ['mikhal']`; it is not permission for a new client to scrape all servers. Refresh is server-side, rate/cooldown constrained and can write remote cache. Prefer Givre's observed prices and approved read API access. [D6]
- Brisage code includes explicitly empirical formulas/estimates and unconfirmed parameters. Treat predictions as estimates tied to an observed coefficient; do not promise guaranteed profit or fabricate an unobserved coefficient for an unattended break loop. [D7]

### BillBot: more account authority than the feature name suggests

Crafting/listing directly changes game state and spends resources/listing fees. The project additionally includes account authentication/registration and subscription/payment workflows. The inspected account scheduler can choose authentication or registration when account automation is enabled; `.env.example` includes `SONJI_API_KEY`, and code includes payment/subscription modules. None of those are required for a native craft/sell module and none should be enabled as an incidental side effect of integrating it. [B1, B2, B5]

Source inspection is not a full outbound/privacy audit. Ankama endpoints and GitHub update checks were identified; no claim is made that all possible network destinations, AI integrations or stored credentials were audited. No credentials were read or requested, and no foreign account was accessed. [B5, B6]
