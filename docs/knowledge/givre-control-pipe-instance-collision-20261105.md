# Local control bridge instance ambiguity — 2026-11-05

During live QA, consecutive read-only calls to the per-user `GivreWork-<hash>` named pipe returned contradictory application states: one reported five configured bots, a later call reported zero. Both responses identified the same source-local app/version and the same shared pipe convention. This makes target identity unreliable when multiple GivreWork windows are running; do not infer the live instance's bot/account state from an unqualified pipe response.

The app's `LocalControlBridge` selects `GIVRE_CONTROL_PIPE` when set, otherwise `ControlPipeClient.DefaultPipeName`, which is derived from the Windows domain and username. The MCP client uses the same convention. Automatic profile isolation was subsequently implemented: when `GIVRE_CLONE_RUN_NAME` is set, the shared client/server resolver derives a QA-specific pipe; an explicit `GIVRE_CONTROL_PIPE` still takes precedence, and no profile retains the default pipe. MCP delegates through the shared client rather than calculating a separate name. Sixteen control/security tests passed, including two simultaneous servers with distinct profiles; a deliberate temporary shared-pipe mutation failed the isolation assertion as expected, then was reverted and the restored 16-test suite passed.

At the latest evidence (2026-11-05), the actual application build and real GUI-bridge validation with a QA profile and no explicit pipe were still in progress/planned. Thus the resolver contract and isolated server tests are validated, but end-to-end wiring in the running GUI is not yet established. Existing open instances continue using their old binaries; do not infer they are isolated. Before issuing state-changing commands, make instance identity explicit and verify it through an instance-specific endpoint; keep existing live clients untouched while diagnosing.

This is a tooling/QA reliability defect, not evidence of data loss or of which window supplied the original responses.
