Screenshot extraction identified Serviette de Plage 13487 with x1=147,x10=1746,x100=4999999,x1000=399999,average621. Exact tax loss is not reconciled.

## 2026-11-06 follow-up: repeated-reprice loss and relaxed configurable guards

The user's HDV concern was confirmed by the journal: Sylvanbot paid about 1.42M kamas in reprice taxes across 7,190 reprices plus 170k listing taxes. A Truite x1000 lot was repriced 5,409 times (about once/second), costing ~413k tax against 160k in sales; Kobalte cost ~597k tax. The profile's configured 30-minute interval was not applied by the watcher. Avoid assuming the earlier fixed 3x ceiling and 10,000-kama per-operation tax cap are acceptable; the user requested controls rather than hard-coded refusals.

The follow-up introduced a 300-second watcher cooldown (manual bulk reprice bypasses it). The 2026-11-07 journal analysis below shows it is keyed by object and lot size, not by individual lot; configurable price ceiling defaulting to 10x with 0 disabling it, and tax cap defaulting to 0/unlimited. Missing reference data no longer blocks a sale. Validation reported 215/215 HDV tests and 4,875 passed/0 failed full-suite tests; isolated release deployed live as PID 36016. Bastionbot, Shadowbot, and Sylvanbot reconnected; active expeditions were resumed (Bastionbot Aerdala after Dojo du Vent's single map was judged unsuitable; Shadowbot Pandala expedition, Sylvanbot's existing activity). Do not treat this as proof of live reprice behavior: deployment/reconnection/activity were checked, but no post-deploy HDV transaction was recorded.

## 2026-11-07 diagnosis: reprice cooldown stalls identical lots

The user reported about 200 lots to reprice with the auto-reprice doing nothing, and that it resumed suddenly after using the "tout sous-coter" button. The journal analysis found: 66 of 92 repriced objects had several identical lots for sale; consecutive reprices of the same object were always at least 60 s apart, with a median gap of 301 s; for example, object 603 in 1000-lot stacks on Bastionbot was lowered 36478 to 36461 one lot per pass at 5-minute intervals. The cooldown therefore counts per object and lot size, so identical lots are repriced one at a time. Bulk "tout sous-coter" ignores the cooldown and explains the sudden burst. Each bot runs its own reprice loop, independent of the character window being viewed.

Implemented 2026-11-07 after the user said to compile and launch: when a pass lowers an object, all of its identical lots (same object, same size) are repriced to the same price in that same pass, and the 5-minute wait is counted from the pass rather than per lot. The HDV tests passed (256/256 in the full run). Not yet confirmed by a live reprice, so treat the live effect as unverified.

Open issue from the same session: the "ouvrir la fenêtre du jeu" button (close the Socket session and relaunch the character in the real Dofus client) produced no log entry between 10:55 and 10:57. Suspected causes, unconfirmed: a reconnection or Enhanced activation already in progress for the account, or a refusal ("La session est occupée ou pas en jeu") while the character is moving, has an exchange or HDV window open, or is speaking to an NPC. Shadowbot and Bastionbot are usually at the HDV in sell mode, and Sylvanbot moves continuously, so the refusal may be frequent. The user's screenshot could not be read because the model in use does not accept images; the displayed message text was needed.

2026-11-07 update: the refusal was a strict version check. The local mapping was 3.7.11.11 while the installed game was 3.7.13.17, so the mirror refused with ScopeMismatch (the Socket session stayed connected). The check now accepts the whole 3.7 family and still refuses an empty version or another family such as 3.8; 5 mirror test cases were added. Not yet live-verified.
