# MZP24 — Reprise ciblée REA + fonctionnalités source-owned

## R — travaux réellement exécutés

L'objectif était de **reprendre la reconstruction** sous `GivreShareWork` sans toucher le GivreClone installé, puis d'ajouter des fonctionnalités testables et d'inspecter les binaires originaux **dans une copie détachée**.

### Améliorations fonctionnelles intégrées

1. **Métiers dans la vue Bots** : nouveau `JobRow` avec les cinq bindings détectés dans les métadonnées Avalonia de l'original (`Icon, Level, Name, Percent, XpText`) ; données alimentées par `JobExperiencesUpdateEvent` et `JobLevelUpEvent` dans le clone. Une valeur d'XP inconnue n'est pas représentée comme une progression de 0 % ; une montée de niveau invalide l'ancien pourcentage. Les noms proviennent de `GameDb.JobData` local si disponible, sinon `Métier #id`. Le panneau est masqué tant qu'aucun métier n'a été annoncé. Détails : `docs/MZP24_JOB_PROGRESS_20261016.md`.
2. **Import groupé de proxys dans l'UI** : formulaire visible dans l'onglet Proxys, aperçu ligne par ligne masqué, erreurs de formats/ports/hôtes, doublons, blocage des imports partiels contenant un rejet, persistence via le stockage DPAPI existant. Aucune connexion ou vérification externe de proxy pendant l'aperçu. Détails : `docs/MZP24_FEATURE_IMPL.md`.
3. **Jeton Zaap à usage unique** : remplacement d'une affectation en expression conditionnelle ambiguë par `ServeTokenOnce`, message de journal exact lors de la première remise et d'un refus de remise ultérieure. Tests sur les deux variantes `auth_getGameToken` / `auth_getGameTokenWithWindowId` ; aucune valeur secrète dans les journaux.

### Reverse engineering des originaux isolés

- `GivreKama.dll` : REA PE/resources + admission managed, SHA épinglé, section massive atypique et seulement quatre imports PE visibles ; comparaison de structure avec le module C++ source-owned, **sans preuve de code identique ni hook réel**. Voir `docs/MZP24_MODS_KAMA_REA.md` et `artifacts/MZP24Binary/`.
- `GivreMcp.exe` : inspection native sous `docs/MZP24_BINARY_DECOMP_REA.md` et `artifacts/MZP24REA/`. Copie identifiée par SHA, point d'entrée RVA `0x115A80`, 6 335 plages `.pdata`, 185 références IAT décodées et vérifiées ; `verify_static.py` a terminé par `MZP24_VERIFY_STATIC_COMPLETE`. L'appel REA/Ghidra MZP24 a cependant abouti à **provider_timeout**, et le premier post-script headless a échoué : **pas de pseudocode métier certifié dans cette passe**.
- `GivreMods.dll` : le rapport distinct `docs/MZP24_MODS_REA.md` n'était **pas encore livré** au gel de ce récapitulatif ; ne pas attribuer des features originales à ce module avant une analyse vérifiée.

## B — ce qui manque toujours pour annoncer un clone « identique »

1. L'analyse Ghidra de binaires natifs empaquetés ne permet pas automatiquement de récupérer tout le code, les algorithmes ou les clés de comportement. Les features sont reconstruites à partir de preuves REA, de contrats existants et de spécifications, pas revendiquées identiques sans comparaison comportementale.
2. Le mapping Protobuf 3.7 est encore **candidat**. Le build final affiche dans la fenêtre une alerte `Mapping incomplet` annonçant **8 messages essentiels manquants** ; ne pas autoriser un test gameplay pour contourner cette alerte. Les tests purs ne certifient ni l'identité d'un processus de test, ni les octets réellement transmis, ni une réponse serveur/ACK.
3. Les parcours lancement Launcher 2, Zaap, transport, gameplay, gestion réelle de compte, HDV et automatisation H24 n'ont pas été certifiés de bout en bout sur un compte de test dans ce lot.
4. La suite xUnit complète du projet comportait **111 échecs de référence** dus notamment à des fixtures historiques/incompatibilités de mappings. Des tests ciblés réussis ne corrigent ni ne rendent verts ces anciens tests.
5. L'interface d'import proxys et la carte Métiers doivent être validées dans le clone avec données de test, puis les flux réellement connectés dans un environnement autorisé. Ne pas confondre compilation/XAML et comportement opérationnel.
