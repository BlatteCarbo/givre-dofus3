# MZB recovery and GivreClone parity

Date: 2026-10-30. Recovery was performed afresh, without reattaching earlier tasks.

## Result and confidence

Recovered the managed browser-authentication component as seven C# implementation files plus assembly metadata, five original binaries under neutral filenames, ASCII/UTF-16 string inventories, eight configuration field schemas, and a suspended main-image memory capture. **The main bot source was not recovered.** The memory image is still packed; it is not an unpacked executable or recovered C#.

The user's "3.6" target could not be authenticated as a semantic product version. The local installer is named `MizanBot-Setup-1.3.6.exe`; the installed main executable and managed helper report `1.0.0` in their version resources. This report identifies the actual installed payload by SHA-256, not by an assumed version. The older Downloads `MizanBot-Setup-1.3.4` directory is a separate distribution and was not substituted for the installed target.

All recovered directory and file names use MZB aliases where the original product name occurred. Original literals inside code, original-source paths in provenance, and raw binary contents remain intact except that the decompiled C# namespace and project assembly name were changed to `MZBLauncher.WebAuth`. These naming changes are not a claim of source ownership or a functional port.

The comparison is **static, not a live parity certification**:

- **present**: a matching capability has concrete code in the clone. This does not prove live game operation or equivalence to protected MZB algorithms.
- **partial**: a related capability exists, but an observed option, implementation, integration, or recovered contract differs.
- **missing**: no counterpart was found in the inspected clone paths. This is not proof that no other independently implemented equivalent exists.
- **Code evidence** means a real recovered managed type/method. **Schema evidence** proves a persisted field exists, not what its protected implementation does. **String evidence** proves the literal exists, not that a code path is reachable.

Clone paths below are relative to `%USERPROFILE%\.t3\worktrees\GivreWork\fix-f01-f16-final-20261024`. Recovered paths are relative to this directory. `WA/` abbreviates `decompiled/webauth/MZBLauncher.WebAuth/`. Rank combines practical value and the specificity of the recovered evidence; gaps with uncertain semantics are not presented as verified bugs.

## What was tried and what remained protected

1. Enumerated target processes and the standard Program Files, local/roaming AppData, Downloads and Desktop locations. Found installed payload under `%LOCALAPPDATA%\Mizan\app`, update package `Mizan\update\pkg.zip`, a separate older unpacked Downloads directory, and a `1.3.6`-named installer. No target process was running. No existing task/debugger session was reattached.
2. Inspected the update ZIP entry list: it contains the application/native libraries/WebAuth/runtime dependencies, not a separate source archive.
3. Installed local `ilspycmd` **11.2.0.10050** under `tools/ilspy`. Direct static project decompilation succeeded on the managed WebAuth DLL. All four main/native modules were individually passed to ILSpy; each exited **70**, `MetadataFileNotSupportedException: PE file does not contain any managed metadata.` Exact output is under `logs/*.ilspy.txt`.
4. Parsed PE sections, CLR directories and .NET single-file bundle signatures using `inspect_bundle.py`. All five target modules lack a .NET single-file bundle marker. Only the WebAuth DLL has a CLR directory. Main `.text` virtual size is 36,412,680 bytes with **raw size 0**; its `.rdata`, `.data`, `.pdata` are also zero-raw sections. Kama/Mods likewise have zero-raw code/data and randomized large backing sections. This is direct evidence of native packing, not a confident identification of a particular packer.
5. Extracted ASCII and UTF-16 printable runs for all five modules to `strings/`. MCP exposes .NET NativeAOT-style runtime/type strings and its pipe/MCP messages. Main/Kama/Mods mostly expose loader/version/manifest residue. No protected combat, scripting, market or native-hook source/types were invented from these strings. `.detourc`/`.detourd` section names in the DLLs are not sufficient evidence to assign a specific hook feature.
6. Attempted `CreateProcessW(CREATE_SUSPENDED)` on neutral-named `dumps/MZBBot.exe`, never resuming its primary thread. First attempt failed with Win32 **740** (elevation required). A materially different second attempt used the inherited `__COMPAT_LAYER=RunAsInvoker` compatibility setting and succeeded without a UAC interaction.
7. The second attempt created **only probe PID 13708**, queried its PEB, read the full mapped main image at `0x7ff653560000`, and saved **185,884,672 bytes** to `dumps/MZBBot.suspended.mapped.bin`. The first 64 bytes of mapped `.text` are all zero; no `BSJB` managed-metadata signature was found. **This is a pre-entrypoint packed image, not a post-unpack dump.** `dumps/memory-probe.json` records the exact observation and successful termination/wait result.
8. Did not resume the protected executable: a suspended map cannot trigger its unpacker; resuming this installed-user executable would execute unknown startup/account/game-integration paths, and there was no verified account-free sandbox or safe post-unpack breakpoint available. Environment-variable substitution alone does not establish isolation from Windows known-folder account storage. No game account login was performed. No dump, injection, suspension or attachment targeted GivreClone or a game client.
9. The `reverse-engineer-anything` skill was not present in the available installed skill tree; deferred-tool discovery found no REA/debugger capability. The local `givre-rea-tools.zip` listing contains Node/pkg and V8 tooling, not an established unpacker for these native PEs. `de4dot` was not run: the protected modules are not IL assemblies, so managed deobfuscation cannot operate on the observed files.

**Still protected/unrecovered:** main bot algorithms and resources inside the native packer; both native DLL implementations; MCP native function bodies and full dynamic tool catalogue; unparsed notification persistence. No post-unpack native dump, original project structure, complete source tree, original build inputs, or live feature equivalence was obtained. Further in-memory recovery would require an account-free isolated execution environment and native unpacker/debugger work; that is not silently represented as completed here.

## Verification and reuse

- Binary preservation completed with exit 0; hashes/sizes are recorded in `manifest.json` and agree with `inventory.json`.
- WebAuth ILSpy decompilation exited 0. Four native ILSpy failures are expected findings, not successful source recovery.
- `python -m py_compile inspect_bundle.py memory_probe.py recover_profiles.py collect_evidence.py` completed in the same exit-0 collection run.
- The memory probe records `terminated: true`, `termination_wait: 0`; a subsequent process query found no PID 13708 and no MZB/original-product process.
- No clone source edits or git commits were made. Clone tests were not run because this task produces forensic artifacts/report only. No recovered code was authenticated against game servers.

Recovery helpers are retained for reproducibility. `inspect_bundle.py` writes inventories/strings; `recover_profiles.py` writes field-only schemas and deliberately excludes account/browser files; `collect_evidence.py` preserves renamed binary copies and decompiler logs. **`memory_probe.py` only creates a suspended probe and terminates it; it does not execute the unpacker.** Do not confuse the `.mapped.bin` layout (RVA-indexed image bytes) with a rebuilt on-disk PE.
